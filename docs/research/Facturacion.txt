Documentación Técnica de Arquitectura: Sistema de Facturación Local (.NET / C#)
1. Principios de Diseño y Capas (Jurisdicciones)
El sistema se rige bajo el principio de separación absoluta de responsabilidades (SRP). Cada capa es soberana en su jurisdicción:
Capa de Presentación (WinForms): Diseñada bajo el patrón Presenter/Controller. No maneja datos directamente, no realiza operaciones matemáticas ni tiene conocimiento de la base de datos.
Capa de Lógica (Dominio Inmutable): Es el cerebro matemático del sistema. Contiene las reglas de negocio, los cálculos de IVAs, subtotales y márgenes. Utiliza modelos puros de datos (POCO/DTO) que actúan como estructuras anémicas y limpias; no conocen cables de red, transacciones ni identidades físicas de almacenamiento.
Capa de Infraestructura (Persistencia / ADO.NET Puro): Es el brazo ejecutor en el mundo físico. Se encarga de las transacciones atómicas, la contención de errores ante cortes de luz o de red, y de traducir los objetos de lógica a modelos físicos de tabla.

2. El Flujo Maestro-Detalle Inmutable (Patrón Memento / Mapeo Externo)
Para evitar corromper la inmutabilidad de la capa de lógica (evitando inyectar métodos mutables como SetNumeroFactura() solo para satisfacer a la base de datos), la persistencia define sus propios Modelos de Tabla (Data Models) con restricciones físicas.
El paso de datos se resuelve mediante un constructor de traducción 1:1 en la capa de infraestructura, lo que respeta SOLID al 100% al mantener la lógica completamente cerrada a modificaciones (OCP).
Estructura del Código Limpio:
// ==========================================
// JURISDICCIÓN DE LÓGICA (Inmutable y Pura)
// ==========================================
public class TicketDetail 
{
    // Solo propiedades de negocio obtenidas de los cálculos planos
    public string Producto { get; }
    public decimal Precio { get; }
    public int Cantidad { get; }

    public TicketDetail(string producto, decimal precio, int cantidad)
    {
        Producto = producto;
        Precio = precio;
        Cantidad = cantidad;
    }
}

// ==========================================
// JURISDICCIÓN DE PERSISTENCIA (Infraestructura)
// ==========================================
public class TicketDetailTable 
{
    // Propiedades exclusivas de las restricciones físicas de la BD
    public int Id { get; set; } // Autoincremental interno
    public string NumeroFactura { get; set; } // La "matrícula" legal correlativa
    
    // Propiedades mapeadas
    public string Producto { get; set; }
    public decimal Precio { get; set; }
    public int Cantidad { get; set; }

    // El constructor 1:1 que salva SOLID e Inversión de Dependencias (DIP)
    public TicketDetailTable(TicketDetail dominio, string numeroFactura)
    {
        // 1. Extrae los datos puros calculados por la lógica
        this.Producto = dominio.Producto;
        this.Precio = dominio.Precio;
        this.Cantidad = dominio.Cantidad;

        // 2. Inyecta la identidad generada durante la transacción física
        this.NumeroFactura = numeroFactura;
    }
}


3. Estrategia de Concurrencia y Transacciones en Red Local
El guardado de una factura es un proceso crítico uno-a-muchos (Cabecera-Líneas). Para garantizar la atomicidad absoluta (o se guarda todo o no se guarda nada), evitar registros huérfanos y neutralizar condiciones de carrera en entornos multipuesto en red local, se aplican tres reglas técnicas:
1. Segregación de Repositorios (CQRS): Las operaciones de lectura y escritura están estrictamente separadas en interfaces independientes (IUserReadRepository e IUserWriteRepository). Esto aísla el comportamiento de la base de datos ante bloqueos de escritura y facilita una futura migración a motores más grandes (como SQL Server) cambiando únicamente la infraestructura.
2. Activación del Modo WAL (Write-Ahead Logging): Configurado nativamente en SQLite. Permite que mientras un puesto retiene la base de datos para la escritura de una transacción pesada de facturación, los demás puestos de la red local puedan seguir realizando lecturas y consultas fluidamente sin congelar la aplicación.
3. Transacción Atómica y Control del Contador: Al procesar la factura, se abre una única transacción donde se lee el contador actual (Contador + 1), se actualiza la tabla de control, se propaga el número real obtenido hacia el constructor del Maestro/Detalles y se ejecuta el bucle de guardado de forma aislada. Cualquier interrupción física (caída de red, corte de energía) aborta el proceso mediante un Rollback, manteniendo el contador y las tablas limpios.

4. Gestión del Ciclo de Vida del Dato en los Controladores
Cada controlador opera de manera autónoma siguiendo el Principio de Responsabilidad Única, aislando sus flujos de control de estado:
Operación Insertar: Valida estrictamente que el objeto cuente con un ID == 0 y que la acción explícita del usuario sea "Nuevo", blindando el sistema contra inserciones duplicadas accidentales.
Operación Editar: Asegura que los cambios se apliquen únicamente si el registro cuenta con un ID > 0 preexistente en la persistencia.
Operación Borrar (Borrado Lógico): Cumpliendo con los estándares de auditoría de software de gestión, nunca se destruyen registros físicos. Al solicitar una baja, se intercepta el objeto (ID > 0) y se conmuta una bandera de estado a nivel lógico (active = false), ocultándolo de las pantallas operativas pero salvaguardando el histórico contable y la integridad referencial del sistema.
